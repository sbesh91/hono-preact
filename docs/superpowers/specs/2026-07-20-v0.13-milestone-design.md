# v0.13 milestone design: "Adoption & Correctness"

Date: 2026-07-20
Status: approved; milestone created and all 25 issues spun out (#258, #311-#334)
Predecessor: v0.12.0 (shipped 2026-07-20, tag `4d45a57e`, 18/18 issues closed)

## Summary

v0.13 is a two-theme release cut against the standing backlog: **adoption &
ergonomics** (the first-run experience and the papercuts that make the obvious
spelling of an API the wrong one) and **quality & correctness** (the surviving
items from the 2026-07-11 framework comparison rerun). A `hono-preact-ui@0.4.0`
cut rides alongside on its own version line.

Scope was chosen deliberately over the smaller alternatives: v0.12 was a
correctness/security cut with no new public API, and the backlog's two tracking
issues (#260, #273) had accumulated ~45 sub-items between them. Taking both
themes in full clears the trackers rather than deferring their tails a third
time.

### Version plan

| Package | From | To | Breaking |
| --- | --- | --- | --- |
| `hono-preact` | 0.12.0 | 0.13.0 | No (additive) |
| `create-hono-preact` | 0.12.0 | 0.13.0 | No (lockstep with framework) |
| `hono-preact-ui` | 0.3.0 | 0.4.0 | **Yes** (#260-5 `onValueChange`) |

"Non-breaking" on the framework line is an **observation about the work as
currently scoped**, not a constraint the work must satisfy. Nothing planned
today breaks the framework's public surface. If a merit-based decision inside an
item calls for a breaking change (A4 is the live candidate: a
`defineAction.unchecked` split is arguably the correct fix and a dev-warn the
stopgap), take the break and update this table. On a 0.x line a minor carries
breaking changes fine, and the release shape must not be the reason a smaller
design wins.

The UI side changes `SelectionProps.onValueChange`'s signature, which is why
0.4.0 is a minor rather than a patch. Per the lockstep policy, `hono-preact-ui` needs its **own
release-notes doc and its own GitHub release**; this is the step that was missed
on v0.11 and must not be missed again.

### Size

29 PRs across three tracks (Track A: 12, Track B: 12, Track C: 5). For
calibration, v0.12 shipped 18 issues across 8 PRs, so this is roughly 3.5x the
PR load of the previous cut. Two items (A5, C1) need a design pass before
implementation; one (B7) is four PRs of structural churn and is sequenced last.

**This count is calibration, not a budget.** There is no release date and no
schedule pressure on v0.13, as with every release on this project. Items are
done right rather than quickly, and none of them should be trimmed, split, or
scoped smaller because of how the total looks. If an item's design comes back
larger than expected, that is information about the item, not a reason to defer
it.

## Mechanics

The sub-items live as checkboxes inside two tracking issues, so they are not
directly milestonable. Follow the pattern established by #282: spin each work
item out into its own issue, assign it to the v0.13 milestone, and leave #260
and #273 open as parents with their checkboxes ticked as work lands. Both
trackers close only when their last child does.

Each track can progress in parallel; the ordering constraints below are within
tracks, not across them.

### A1 before A2 (hard ordering)

#260-2 proposes adding `hoofd` to the template's dependencies, because it is a
required version-coupled peer that the template's pages import by name. A1
re-exports those hooks from `hono-preact`, at which point the template should
not name `hoofd` at all. Landing A2 first means writing a dependency and a set
of imports that A1 then deletes.

### A2 scope (two PRs)

The template refresh is the single largest adoption item and splits cleanly:

1. **Template and scaffolder**: add `"typecheck": "tsc --noEmit"` to
   `templates/base/package.json` (and run `tsc` in the scaffold integration
   test), drop the obsolete `server:` field from `templates/base/src/routes.ts`,
   register typed routes (`as const` + `RegisteredRoutes`), extend
   `substituteName` to cover `Layout.tsx` so `{{name}}` stops rendering
   literally, add a Node version preflight and align `create-hono-preact`'s
   declared `engines` (`>=20`) with the framework's actual requirement
   (`^22.18.0 || >=24.11.0`), and collapse the home page onto the canonical
   single-`.View()` form.
2. **Recipes and docs**: fix the four agent recipes that verify with
   `pnpm typecheck`, correct `add-a-loader.md`'s Common Mistakes section (the
   "forgetting the `server:` import" advice has been factually wrong since
   0.10.0's auto-discovery), regenerate the bundled corpus, and refresh the root
   README (it still says v0.8.0 and shows an extensionless `views/home` import
   that the recipes themselves list as mistake #1).

### A5 and A8 need design before code

A5 introduces a subtree binder (`serverRoute('/demo/projects/*')` or
`serverLayout(path)`) that resolves a node's inherited `use`, plus a dev warning
when a bare loader serves a request whose matched route carries `use`. It is
security-adjacent and touches the same fail-closed discipline as #288 and #178,
so it gets its own design pass. Note the framing: bare-loader route-independence
is by design (the v0.10 review withdrew the P0 on exactly this point). The gap
being closed is ergonomic, not a live vulnerability, and the design must not
regress the deliberate route-independent behavior.

A8's approach is already specified in #258 (a serve-only Vite plugin computing a
dev route to CSS map via `extractRouteChains`, installed through the same
`installPreloadModules` reader seam production uses). The design constraint worth
restating: the docs site runs dev through `@cloudflare/vite-plugin` in workerd,
so `renderPage` cannot reach Vite's SSR module graph. The source-scan approach
exists to sidestep that, and any alternative must work for both the Node and
Cloudflare adapters.

### A9 batching

The #260 second tier holds ~18 non-UI bullets, most of them one-to-three-line
dev-warns, doc corrections, or renames. Batch by subsystem rather than by
priority so each PR touches one area:

- **core/iso**: `useParams` dev-warn on no-match, status-first narrowing docs
  and/or a `match()` helper, `invalidate` tri-mode split, `View` two-parameter
  render, `params` vs `paramsSchema` rename, `mutate`'s post-redirect settle
  arm, `RouteBinder.room` `Data` default drift, `definePage` omission dev-check,
  `buildPath` multi-segment wildcards.
- **vite/adapters**: `process.cwd()` vs `config.root` inconsistency, option
  defaults to `@default` JSDoc, Node adapter cwd-sensitivity, Node dev
  pass-through `exclude`/`include`, CF adapter realtime-DO gating,
  `emitClientAsset` helper.
- **docs + scaffolder**: client-session-hint helper docs, route-bound
  `pathParams` derivation note, mixed bare/bound nudge, `ctx.c` typing note,
  scaffolder install-failure recovery note, scaffold-into-current-dir path,
  AGENTS.md vs recipe export-list contradiction.

Bullets that turn out to need real design rather than a fix get promoted to
their own issue and deferred; do not force them into a batch.

### B7 runs last (hard ordering)

B7 re-homes `server-entry.ts`'s two AST diagnostics and its probe watcher, and
A6 edits the same file to add the config-probe watcher. B7 also rewrites the
`render.tsx` asset-hint policy block, which v0.12 touched. Landing B7 before the
feature work in those files guarantees conflicts and forces the review to
re-verify behavior that had already been verified. Sequence it after A6 and
after Track B's other items.

### B2 must settle the error-code vocabulary, not just add the field

#273-3 asks to carry `code` in the loader RPC deny envelope for parity with the
action envelope. #200-4 separately wants a named, statically-known code
vocabulary (`UNAUTHORIZED`, `NOT_FOUND`, `CONFLICT`, …) decorating `deny` on the
same envelope. Shipping a free-form `code` in v0.13 and a vocabulary later is two
breaking passes over a public wire format.

Decide the vocabulary as part of B2 even if only a subset ships in v0.13. The
rest of B2 stands as filed: surface deny on `mutate`'s imperative result as a
typed failure arm, and thread a type (or a guarded accessor forcing a user
narrow) through `ActionResult`'s deny `data?: unknown`.

### B8 interacts with repo policy

The cast-hygiene sweep is the codified version of the repo's no-inline-casts
rule. Per that policy, each site should be fixed by reshaping the type, not by
relocating the cast; sites that genuinely sit on a sanctioned boundary (parsing
untrusted JSON, FormData reads, structural reads off user module exports) get a
comment saying so rather than a rewrite.

## Track C: `hono-preact-ui@0.4.0` (5 PRs)

| ID | Issue | Work item | Source | Breaking |
| --- | --- | --- | --- | --- |
| C1 | #330 | Select/Combobox generic over `multiple`; `MenuRadioGroup<V>` | #260-5 | **Yes** |
| C2 | #331 | Opt-in `Combobox` `filter` prop | #260 tier 2 | Behavior change |
| C3 | #332 | Render-prop event composition + non-focusable-trigger dev-warn | #260 tier 2 | No |
| C4 | #333 | Toast / ContextMenu data-attr conventions + Value-part channels | #260 tier 2 | Styling contract |
| C5 | #334 | Mid-level Listbox / Command part set | #260 tier 2 | No |

Two items beyond C1 carry migration weight, noticed while writing the issues and
corrected here: **C2** changes default behavior (a `Combobox` that previously
showed every option now filters), and **C4**'s `data-expanded` change is a
**styling contract** break for anyone selecting on `[data-expanded="false"]`.
Neither changes the version plan, since 0.4.0 is already a breaking minor, but
both need a line in the migration section of the ui release notes.

C1 needs a design pass. The target shape from #260-5 is discriminated props on
the Root generic: single-select gets `value?: Value` and
`onValueChange?: (v: Value | null) => void` with `null` meaning cleared, multi
gets `Value[]`. The evidence that this is worth the break is that every consumer
including the package's own docs demos currently does an `Array.isArray` dance,
and the site invented a `''` sentinel plus a synthetic "Unassigned" option
because controlled-empty is unrepresentable.

Verification for the whole track runs through `apps/site`: each PR should delete
the corresponding workaround from the demo code, and the demos are the proof the
new shape is usable.

## Risks

These are risks to **correctness and coherence**. Schedule is not a risk on this
project; see the note under Size.

- **B7 is the merit risk, not a schedule risk.** Decomposition is the one kind of
  change that can be entirely behavior-preserving and still make the codebase
  worse, by scattering logic that read better together. Each of its four PRs
  needs a real argument that the extracted shape is better, and its sub-item 4
  (the shared loader/action invocation engine) is explicitly a "consider":
  closing it unchanged with a recorded finding is a legitimate outcome.
- **A4's shape is an open design question, not a foregone dev-warn.** The
  finding is that the obvious spelling of `defineAction` is the unsafe one. A
  dev-warn tells the author after the fact; `defineAction.unchecked` makes the
  unsafe path visible at the call site permanently. The second is plausibly the
  correct fix and is breaking. Decide it on merit inside the issue.
- **A5 and C1 could each expand.** Both are design-first for that reason. If
  either design comes back larger than a single PR, build the larger thing.
- **Corpus regeneration is easy to miss.** A2's recipe changes flow into the
  bundled `llms-full.txt` via `pnpm gen:agents-corpus`; the corpus is gitignored,
  so a stale local copy is a local-only failure that surfaces in CI.
