## What v0.13 actually is now

The original framing was "Adoption & Correctness", with adoption as the headline
theme. **That theme is gone** — the adoption work (template refresh, action
error masking, bare-loader gates, config probes, head-hook re-exports,
`createCaller` streaming) all shipped in the #261-#269 wave.

The theme is therefore **"Hardening & Ergonomics"** (maintainer call,
2026-07-20). The substantive core is the #273 correctness sweep: fail-closed
discipline (#321), deny-path parity (#322), a build-time whitelist bypass
(#335), unguarded queues and silent degrades (#325), and cast hygiene (#328).
Around it sit the #260 second-tier ergonomics bullets and `hono-preact-ui`
polish. The task list is unchanged from the post-sweep set; only the framing
moved to match what the work actually is.

### #258's filed symptom no longer reproduces

An earlier revision of this document called `render.tsx:246-250` a "new blocker".
**That was a misreading, now corrected on the issue.**

`apps/site` has **no route-scoped CSS files**: `styles/root.css` is a single
5307-line sheet, and the only `import '...css'` occurrences in the site are
example code inside `pages/docs/styling.mdx`. `d86b8242` replaced hand-split
sheets with build-time auto-splitting; in dev nothing splits, so every rule is
present on first paint.

The `devGlobalCss ? [] : ...` line is a **correct guard**, not an obstacle: per
its comment at `:234-245`, a stale `dist/client` still reads in dev on the node
adapter, so artifact route-sheet URLs would 404 *render-blockingly*. Any dev
injection must use dev **source** URLs — which the issue's recommended
source-scan approach already does, so the approach was right and only the
blocker framing was wrong.

What survives is narrower: a user project that **hand-splits** still flashes in
dev, while `styling.mdx:77` promises route sheets are "always render-blocking,
present for first paint with no flash of unstyled content". True in prod, false
in dev. Recommended order: fix the false promise in the docs first (one line),
then decide whether dev parity justifies a serve-only plugin — noting there is
**no reproduction in this repo**, so implementing it needs a hand-split fixture
project, which is most of the work.

### B2's central instruction was wrong and is withdrawn

The first version of this spec instructed B2 to "settle the error-code
vocabulary, not just add the field", on the reasoning that shipping free-form
`code` now and a named vocabulary later would be two breaking passes over a
public wire format.

**That premise was false.** The full `DenyCode` vocabulary (8 members) plus
`DENY_CODE_STATUS` shipped in `83555bc9` (#200 / PR #210) on **2026-06-29** —
almost two weeks *before* the #273 audit that filed the item — with round-trip
tests. #200 item 4 is already checked off. Nothing needs designing; B2 is three
plumbing tasks: carry `code` in the loader deny envelope end to end, give
`mutate` a typed deny arm, and type `ActionResult`'s deny `data`.

### B6 contained a correctness hole; it is now #335

`server-loader-validation.ts:48-57` collects `FunctionDeclaration` and
`VariableDeclaration` only, so `export class Foo {}` parses to a
`ClassDeclaration`, never lands in `namedExports`, and **bypasses the
`RECOGNIZED_SERVER_EXPORTS` check at `:62-68` entirely**. The guard reports
success on a module it never checked. Verified directly against source.

Split out of the test-gap batch into **#335** and labelled `bug` / P2. The fix
should make the collection **exhaustive over declaration node types** rather
than adding two more `else if` arms, so the next unhandled TS node type
(`TSEnumDeclaration` is the obvious next one) fails loudly instead of passing
silently.

## Risks

Risks to **correctness and coherence**. Schedule is not a risk on this project.

- **The trackers cannot be trusted as planning input.** This document's first
  version is the proof. Anything sourced from #260 or #273 must be re-verified
  against source before work starts. The per-issue comments dated 2026-07-20
  carry that verification; work from those, not from the issue bodies.
- **B7 is a merit risk.** Decomposition can be entirely behavior-preserving and
  still leave the codebase worse by scattering logic that read better together.
  Each PR needs an argument that the extracted shape is better. Sub-item 4 is
  explicitly a "consider": closing it unchanged with a recorded finding is a
  legitimate outcome.
- **A4 is a genuine open design question**, not a foregone conclusion in either
  direction. The dev-warn is shipped, tested, and caught the real cases; a
  second mechanism for the same defect class may be redundant surface. Equally,
  the finding's evidence was a review-legibility problem that a dev-warn does
  not address. Decide on merit and record the reasoning.
- **The ui cut may not deserve a minor.** See the version plan.
