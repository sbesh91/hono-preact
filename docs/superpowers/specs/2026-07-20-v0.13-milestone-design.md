## What v0.13 actually is now

The original framing was "Adoption & Correctness", with adoption as the headline
theme. **That theme is gone** — the adoption work (template refresh, action
error masking, bare-loader gates, config probes, head-hook re-exports,
`createCaller` streaming) all shipped in the #261-#269 wave.

What remains is honestly characterised as a **quality and ergonomics-tail
release**: the #273 correctness sweep as the substantive core, plus the
second-tier ergonomics bullets, the dev-only route-CSS gap, and small UI polish.
Whether that is the release worth cutting next, or whether v0.13 should instead
be reshaped around the public-API work now sitting in the deferred pile, is an
open question for the maintainer.

and #333 (`data-expanded` is a styling contract consumers select on). Both are
real but weaker. A `0.3.1` patch is arguably the better fit if #331 and #333 are
descoped.

### B2's central instruction was wrong and is withdrawn

The first version of this spec instructed B2 to "settle the error-code
vocabulary, not just add the field", on the reasoning that shipping free-form
`code` now and a named vocabulary later would be two breaking passes over a
public wire format.

**That premise was false.** The full `DenyCode` vocabulary (8 members) plus
`DENY_CODE_STATUS` shipped in `83555bc9` (#200 / PR #210) on **2026-06-29** —
almost two weeks *before* the #273 audit that filed the item — with round-trip
tests. #200 item 4 is already checked off. Nothing needs designing; B2 is three
plumbing tasks: carry `code` in the loader deny envelope end to end, give
`mutate` a typed deny arm, and type `ActionResult`'s deny `data`.

### B6 contains a correctness hole, not just a coverage gap

`server-loader-validation.ts:48-57` collects `FunctionDeclaration` and
`VariableDeclaration` only, so `export class Foo {}` in a `.server.ts` never
lands in `namedExports` and **bypasses the `RECOGNIZED_SERVER_EXPORTS` whitelist
check at `:62-68` entirely**. That is a latent whitelist bypass with a missing
test attached, and it should be prioritised as such rather than batched as
coverage polish.

### B7 sequencing (unchanged, and confirmed)

B7 still runs after A-track work that touches the same files. The original
rationale was verified: `82bce1c5` (v0.12) did touch the `render.tsx` region B7
rewrites, and v0.12's `#287` work added the `serverDeny` application immediately
above it, so that file has *more* in it than when the item was filed.

## Risks

Risks to **correctness and coherence**. Schedule is not a risk on this project.

- **The trackers cannot be trusted as planning input.** This document's first
  version is the proof. Anything sourced from #260 or #273 must be re-verified
  against source before work starts. The per-issue comments dated 2026-07-20
  carry that verification; work from those, not from the issue bodies.
- **B7 is a merit risk.** Decomposition can be entirely behavior-preserving and
  still leave the codebase worse by scattering logic that read better together.
  Each PR needs an argument that the extracted shape is better. Sub-item 4 is
  explicitly a "consider": closing it unchanged with a recorded finding is a
  legitimate outcome.
- **A4 is a genuine open design question**, not a foregone conclusion in either
  direction. The dev-warn is shipped, tested, and caught the real cases; a
  second mechanism for the same defect class may be redundant surface. Equally,
  the finding's evidence was a review-legibility problem that a dev-warn does
  not address. Decide on merit and record the reasoning.
- **The ui cut may not deserve a minor.** See the version plan.
