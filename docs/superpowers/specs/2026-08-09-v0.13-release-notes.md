# hono-preact v0.13.0

**Released:** 2026-08-09

The largest cut since the framework opened. Three things happen at once, and the
first is the one to read before you upgrade:

1. **Signals are the data layer.** Four hooks and the room roster now return
   signals instead of plain values, so reads move behind `.value`. This is a
   redesign, not a rename, and some of it is invisible to the compiler.
2. **The middleware scope tags finally enforce something.** They had measured
   bivariant since they were introduced, so every `<'page'>` / `<'loader'>` /
   `<'action'>` tag was an unchecked comment. They bind now, which means two
   slots that had been quietly lying about their scope stop compiling.
3. **Hardening.** A deny now carries its code end to end, `mutate()` reports a
   denial as its own arm instead of a flattened `Error`, and four silent
   failures (a bypassed export whitelist, a misconfigured `base`, an unbounded
   queue, a dropped middleware entry) became loud.

New capability is small and additive: `<For>` and `<Show>`, and a deny-data type
that infers from your guards.

## Before you install

Two install-level requirements changed, both from the signals work:

- **`preact` peer floor is now `>=10.25.0`** (was `>=10.0.0`).
- **`@preact/signals` is a dependency of the framework**, not something you add.
  Import `signal`, `computed`, `useSignal` and the rest from `hono-preact` so
  you get the framework's copy; a second copy in your own dependencies fails
  quietly, because the library keeps its bookkeeping in module state and a
  computed in one copy never hears from a signal in the other.

One consequence worth knowing: importing `@preact/signals` at all turns on
prop-level memoization for components that touch a signal. That is the library's
behavior, not something the framework implements, and it is usually a free win.

One build note for the release engineer: `tsc` never cleans `dist`, and `files`
ships `dist`, so a stale artifact from a deleted source file would be published.
Wipe `dist/` before the release build.

## Do I have to do anything?

Yes. Read the **Silent** rows first: those compile and behave differently.
**Compiler-caught** means `tsc` points at the line. **Cosmetic** means nothing
to do.

### The data layer (#342)

| Symbol | Severity | Action |
|---|---|---|
| `useActionResult()` | **Silent** | Returns a signal, so `if (result)` is now always true (a signal object is truthy). Test `result.value`. |
| `useRoom().self` | **Silent** | A signal, so `if (self)` is always true. Test `self.value`. |
| `useRoom().members` | Compiler-caught | A signal: `members.value.length`. The `.length` read does not compile against a signal, so this one the compiler catches. |
| `loader.useData()` | Compiler-caught | Read `.value`, or hold the signal and read it at the point of use for finer re-render granularity. |
| `useFormStatus()` | Compiler-caught | Read `.value`. Do not compare the result to a `FormStatus` literal by identity; read `.pending`. |
| `useOptimistic()` | Compiler-caught | The tuple's first element is a signal: `movies.value.map(...)`. Assigning to it now throws a `TypeError` where it used to be a silent no-op, and `base` is compared one level deep rather than by reference. |
| `FieldErrorsMap` | Compiler-caught | Messages are `readonly string[]`. Copy before `.sort()` / `.reverse()`. |
| `subscribeFormSubmit` / `subscribeLastActionResult` | Compiler-caught | Removed from `hono-preact/internal`. Use `pendingSignal` / `lastActionResultSignal`. |
| `preact` peer / `@preact/signals` | Install-time | Bump `preact` to `>=10.25.0`. Do not add `@preact/signals` yourself; import the primitives from `hono-preact`. |

The compiler catches most of this, because a signal has none of the properties
the old value had. It does **not** catch a truthiness gate, a dependency array
that now holds a stable signal reference, a sink typed `unknown` or `any`, or
string and JSON coercion (a signal stringifies as `[object Object]`). The
migration guide walks each hazard with a way to find it:
`2026-07-27-signals-migration-release-notes.md`.

### Everything else

| Symbol | Severity | Action |
|---|---|---|
| `Next` / `next()` | **Silent** | Stop reading what `next()` resolves with; it is now `undefined`. Take the value from the loader or action itself. |
| `eventStream` queue | **Silent** | The FIFO is capped at 128 payloads where the docstring used to promise unbounded. A stalled consumer now drops the newest arrivals and warns once. Drain promptly, or expect drops under backpressure. |
| `MutateResult` (`mutate()`) | Compiler-caught | Now three arms. `if (!result.ok) result.error` no longer typechecks: switch on `result.kind` (`'deny'` carries a `deny` record, `'error'` an `Error`). |
| `use` entries | Runtime, fail-closed | A malformed `use` entry used to be silently reclassified as an observer, which never gates a request. It now throws when the chain is composed, surfaced as the normal error envelope. A middleware that was quietly not running will start failing loudly. |
| `ServerMiddleware<S>` | Compiler-caught | Drop the scope argument on any middleware that lands in an app-level or route-level `use`. |
| `AppUseElement` (`defineApp({ use })`) | Compiler-caught | Replace `defineServerMiddleware<'page'>(...)` with `defineServerMiddleware(...)` and narrow on `ctx.scope`. Move any `defineClientMiddleware(...)` entry to a route node's `use`; at the app level it never ran (#359). |
| `RouteDef['use']` | Compiler-caught | Same fix as the app tier for server entries. If you annotate the array, use the new `RouteUseElement[]`. |
| `SocketHandler['use']` / `RoomHandler['use']` | Compiler-caught | Retag a reused `<'page'>` or `<'action'>` guard as `<'loader'>`, or drop the tag. |
| `Middleware` | Compiler-caught | A `Middleware[]` annotation no longer fits a `use` slot. Use `AppUseElement[]` (app tier) or `RouteUseElement[]` (route tier), or let the array infer. |
| `LoaderFn` | Compiler-caught | Params move from generic slot two to slot three. A streaming loader needs `true` in slot two. |
| `ServerCtx<S>` | Cosmetic | Nothing. It resolves to the same type for every `S` it did before. |
| `NavLinkProps` | Cosmetic | Nothing. Additive: `target` / `rel` / `download` now typecheck. |
| Render-prop handlers (`hono-preact-ui`) | **Silent** | A handler you passed on a `render` vnode used to be dropped and now fires, composed before the part's own. See the ui notes. |

## Breaking: signals are the data layer (#342)

Four hooks and the room roster return signals now. The shape of the change is
the same everywhere: what you used to read directly, you read through `.value`.

```tsx
// before
const state = moviesLoader.useData();
if (state.status === 'success') return <List movies={state.data.movies} />;

// after
const state = moviesLoader.useData();
if (state.value.status === 'success')
  return <List movies={state.value.data.movies} />;
```

The point of the redesign is granularity: a binding that reads only `.value`
inside a small leaf re-renders on its own, without the surrounding tree. Holding
the signal and reading it where you display it is the idiomatic shape, and
`useComputed` projects a field the same way.

The full migration guide, including the four hazards the compiler cannot catch
and how to grep for each, is
`docs/superpowers/specs/2026-07-27-signals-migration-release-notes.md`. Read it
before upgrading a large app; it is the one document in this release that will
save you real time.

The cost is a one-time toll of roughly 5.6 KB gzip for an app that uses the data
layer, not a per-feature charge.

## Breaking: the middleware scope family

Six of these are one defect seen from six angles, and they share one migration:
**drop the scope argument and narrow on `ctx.scope`, reserving the scope argument
for a single unit's own `use`, where exactly one context shape can arrive.** The
first two explain why; the rest are the slots where it lands.

### `ServerCtx<S>` is spelled as an indexed access, not a conditional chain (#351)

The three context shapes did not change, and neither did what `ServerCtx<S>`
resolves to for any `S`. `ServerCtx<'page'>` is still exactly `ServerPageCtx`;
`ServerCtx<Scope>` is still exactly the union of all three. Only the spelling
changed:

```ts
// before
export type ServerCtx<S extends Scope = Scope> = S extends 'page'
  ? ServerPageCtx
  : S extends 'loader'
    ? ServerLoaderCtx
    : S extends 'action'
      ? ServerActionCtx
      : ServerPageCtx | ServerLoaderCtx | ServerActionCtx;

// after
export type ServerCtx<S extends Scope = Scope> = {
  page: ServerPageCtx;
  loader: ServerLoaderCtx;
  action: ServerActionCtx;
}[S];
```

That looks like a refactor with nothing behind it, so here is why it is listed
as a break. The spelling decides the variance TypeScript measures for everything
built on top of it. With `S` sitting in a conditional's check position, both of
the compiler's variance probes fall through to the same final branch, so the two
instantiations came out identical and `ServerMiddleware<S>` measured
**bivariant** in `S`.

Bivariance relates two instantiations when the scope tag matches in *either*
direction, and that opened one specific hole: `ServerMiddleware<'page'>`
satisfied a `ServerMiddleware<Scope>` slot. That is the unsound direction. A
middleware written against `ServerPageCtx` would sit in a slot the framework
dispatches with a loader or an action ctx, and the app-level and route-node
`use` tiers are exactly such slots, because `composeServerChain` folds them into
the loader and action chains as well as the page render. An indexed access
measures contravariant, which is what a parameter position means, so that
assignment is now rejected while the reverse still compiles.

One calibration, so you do not go hunting for a bug that was not there: the old
spelling was not a free-for-all. Two disjoint tags never related in either
direction, so `ServerMiddleware<'page'>` and `ServerMiddleware<'loader'>` were as
unassignable to each other before this change as after it. The hole was on the
`Scope` axis alone.

So the type alias itself costs you nothing. If you name `ServerCtx<'page'>` (or
`<'loader'>`, `<'action'>`, or the bare `ServerCtx`) anywhere, it means the same
thing it meant in 0.12.0 and keeps compiling. The consequences all land on
`ServerMiddleware`, next.

### `ServerMiddleware<S>` is contravariant in `S` (#351)

The declaration is textually unchanged. What changed is that the scope argument
now binds, because `ServerCtx<S>` measures contravariant (above). One direction
of assignment that used to compile no longer does: a middleware tagged with a
single scope no longer satisfies an all-scope slot.

```ts
declare const all: ServerMiddleware<Scope>;    // defineServerMiddleware(fn)
declare const page: ServerMiddleware<'page'>;  // defineServerMiddleware<'page'>(fn)

const a: ServerMiddleware<'page'> = all;    // fine, and always was
const b: ServerMiddleware<'loader'> = all;  // fine, and always was

const c: ServerMiddleware<Scope> = page;    // NOW A TYPE ERROR

// Unchanged: one scope tag never satisfied a different one.
const d: ServerMiddleware<'loader'> = page; // error before, error now
```

That last line is worth calling out, because it is the case people expect to
have changed and it did not. Mismatched scope tags always failed. The single
unsound direction was a tagged middleware flowing into an all-scope slot, which
compiled and should not have.

Why it was wrong is easier to see in the slot that motivated it. `AppConfig`'s
`use` and a route node's `use` were both typed `ServerMiddleware<'page'>`, each
with a comment asserting that tier only runs in page scope. It does not.
`composeServerChain` folds `[appConfig.use, resolvePageUse(path), unitUse]` into
the loader chain and the action chain as well as the page render, deliberately,
because those outer tiers are where auth gates live. So an entry promised a
`ServerPageCtx`, whose `location` is always present, was in fact handed a
`ServerActionCtx`, whose `location` is optional. A guard reading
`ctx.location.pathParams.orgId` throws, or optional-chains to `undefined` and
may read that as unrestricted.

The dispatch is correct and is untouched. Narrowing it so those tiers only ran
in page scope would drop app-level and route-level guards off loaders and
actions, which is an auth bypass, not a fix. The types were the liars.

On its own this variance change breaks nothing you had written: before the
reshape, widening a slot to `ServerMiddleware<Scope>` would have compiled and
enforced nothing. It is the enabler. It is what makes the retyped `use` slots in
the next entries actually reject a mis-scoped entry instead of silently
accepting it.

Read the parameter the way you would read a function parameter.
`ServerMiddleware<Scope>`, the default you get from `defineServerMiddleware(fn)`
with no type argument, is the **strictest** form and not the loosest: its `fn`
has to accept the whole context union, so it is the only shape that survives
wherever the framework decides to call it. `ServerMiddleware<'page'>` is a
narrower promise, and it now fits only where exactly a page context can arrive.

The migration is to drop the type argument on anything that lands in a slot the
framework dispatches in more than one scope, and to handle the union:

```ts
// Before: compiled, and was promised a `location` it did not always get.
export default defineApp({
  use: [
    defineServerMiddleware<'page'>(async (ctx, next) => {
      const org = ctx.location.pathParams.orgId;
      await next();
    }),
  ],
});

// After: all-scope, and `location` reads as `RouteHook | undefined`.
export default defineApp({
  use: [
    defineServerMiddleware(async (ctx, next) => {
      const org = ctx.location?.pathParams.orgId;
      if (!org) throw deny(403, 'no route scope');
      await next();
    }),
  ],
});
```

Keep the tag only where the slot really is single-scope, such as a loader's or
an action's own `use`. The practical fallout lands in the `use` slots below, the
places where the framework hands one entry more than one context shape.

### `defineApp({ use })` requires all-scope middleware (#351)

`AppUseElement` was typed `ServerMiddleware<'page'>`, on the stated grounds that
app-level `use` runs in page scope. It does not. `composeServerChain` folds
`appConfig.use` in as the outermost tier of the **loader** chain and the
**action** chain as well, and those handlers dispatch it with a
`ServerLoaderCtx` / `ServerActionCtx`. That is what "app-level" means, and it is
deliberate: the outer tiers are where auth gates live, so narrowing the dispatch
instead would drop an app-tier guard off the loader and action paths, which is a
bypass rather than a fix. The types were the liars.

```ts
// before
export type AppUseElement =
  | ServerMiddleware<'page'>
  | ClientMiddleware
  | StreamObserver<unknown, never>;

// after
export type AppUseElement =
  | ServerMiddleware<Scope>
  | StreamObserver<unknown, never>;
```

The `ClientMiddleware` arm is gone too, for the inverse reason (#359): where
the `<'page'>` tag promised less than the dispatch delivered, the
`ClientMiddleware` arm promised more. App config never enters the client
module graph (the generated client entry imports only the routes;
`bootClient()` takes no config), so an app-level `defineClientMiddleware(...)`
entry typechecked, shipped, and never ran. Attach client middleware to a route
node's `use` instead, which the client dispatcher does see; on a node that
wraps all your routes it runs on every navigation, which is what the
app-level placement appeared to mean. Nothing behavioral changes: such an entry was
already doing nothing.

The field that made this worth breaking is `location`. `ServerPageCtx` promises
a `location` that is always present; on the bare-action context it is optional
and genuinely absent. So this compiled, and shipped:

```ts
// before: typechecked, because ctx was a ServerPageCtx
const requireOrgMember = defineServerMiddleware<'page'>(async (ctx, next) => {
  if (!(await mayAccess(ctx.c, ctx.location.pathParams.orgId))) {
    throw deny('FORBIDDEN');
  }
  await next();
});
export default defineApp({ use: [requireOrgMember] });
```

On a bare `defineAction` POST that guard is handed a context with no `location`
at all. It throws, or, if the author reached for `?.` to quiet an editor, it
evaluates `undefined` and reads the result as unrestricted. Both outcomes are on
the authorization path.

**Migration.** Drop the scope argument and narrow on `ctx.scope`:

```ts
// after
import { defineApp, defineServerMiddleware, deny } from 'hono-preact';
// `render` is page-scope only, so it lives on the page subpath.
import { render } from 'hono-preact/page';

const adminOnly = defineServerMiddleware(async (ctx, next) => {
  const user = await currentUser(ctx.c);
  if (!user?.isAdmin) {
    // `render` replaces a page tree, so it only means anything in page scope.
    if (ctx.scope === 'page') throw render(NotAuthorized);
    throw deny('FORBIDDEN');
  }
  await next();
});

export default defineApp({ use: [adminOnly] });
```

Off the all-scope context, `ctx.location` reads as `RouteHook | undefined`,
which is the check an app-tier guard has to make and exactly what the old typing
let an author skip. Absent is not "unrestricted": fail closed
(`if (!ctx.location) throw deny('FORBIDDEN')`) unless you mean otherwise.

The scope argument is still correct, and still worth writing, on a **single
unit's own** `use`. A loader's `use` is dispatched only in loader scope and an
action's only in action scope, so exactly one context shape can arrive and
`defineServerMiddleware<'loader'>(...)` / `<'action'>(...)` fit there unchanged.
Reserve it for those.

The error is unmissable if you do nothing:

```
error TS2322: Type 'ServerMiddleware<"page">' is not assignable to type 'AppUseElement'.
  Type 'ServerMiddleware<"page">' is not assignable to type 'ServerMiddleware<Scope>'.
    Type 'Scope' is not assignable to type '"page"'.
      Type '"loader"' is not assignable to type '"page"'.
```

### A route node's `use` in `defineRoutes` requires all-scope middleware (#351)

Same fix, one tier down. A `RouteDef`'s `use` was typed
`ServerMiddleware<'page'>`, and a route node's `use` does not run only in page
scope. It runs on the node's own page render, `composeServerChain` folds the same
tier (`resolvePageUse(path)`) into that route's loader chain, and it folds it
into the chain of any action bound to the route with `serverRoute(r)`. A route
guard is a route guard on all three paths, which is the point of putting it on
the route node.

So a `<'page'>` entry there was promised a `ServerPageCtx` and handed a
`ServerLoaderCtx`, or a route-bound `ServerActionCtx`, instead. What breaks is
narrower than at the app tier: a route node's `use` never runs on a bare
`defineAction`, so `ctx.location` really is present here. The scope promise is
the false one. `throw render(...)` from a route guard renders on the page path
and comes back as a 500 on that same route's loader RPC, because `render` is a
page-scope outcome the loader RPC has no way to honor.

```ts
// before: compiled, wrong on the loader and action paths
export const routes = defineRoutes([
  {
    path: '/admin',
    use: [defineServerMiddleware<'page'>(adminGate)],
    view: () => import('./Admin.js'),
  },
]);

// after
export const routes = defineRoutes([
  { path: '/admin', use: [adminOnly], view: () => import('./Admin.js') },
]);
```

where `adminOnly` is the all-scope, `ctx.scope`-narrowing middleware from the
`defineApp({ use })` entry above. A server guard takes the same shape at either
tier, so one guard can be attached to both; the route tier additionally admits
`ClientMiddleware`, which the app tier does not (#359, above).

Two annotations to check while you are in there. `Middleware[]` no longer fits:
`Middleware` is the unknown-scope union (it admits a
`ServerMiddleware<'loader'>`), not the all-scope shape this slot needs. If you
want to name the element type, the new export `RouteUseElement` is the element
type of a route node's `use`, so `RouteUseElement[]` annotates it correctly
(`AppUseElement[]` also fits, but rejects client middleware, which this tier
supports). The docs table for `RouteDef` said `Middleware[]` through 0.12.0 and
now says `RouteUseElement[]`.

As at the app tier, the scope argument remains correct on a single loader's or
action's own `use`, where only one context shape can arrive.

### `SocketHandler['use']` and `RoomHandler['use']` are typed for loader scope (#351)

Both slots were `ReadonlyArray<Middleware>`, and under the old bivariant
`ServerMiddleware<S>` that accepted a guard carrying any scope tag at all. They
now name the one context that can actually arrive:

```ts
// before
use?: ReadonlyArray<Middleware>;

// after
use?: ReadonlyArray<ServerMiddleware<'loader'> | ClientMiddleware>;
```

Loader scope specifically, because a WebSocket upgrade is an HTTP GET carrying a
Hono context, and `socket-resolution.ts` builds a `ServerLoaderCtx` for the guard
probe: `scope: 'loader'`, a `location` derived from the route pattern and the
resolved path params, and `module` / `loader` set from the socket's module key
and name. It composes that chain with `composeServerChain<'loader'>` and
dispatches it with `dispatchServer<true, 'loader'>`. There is no page render and
no action payload anywhere on that path, so unlike the app and route tiers
(which widened in this same release, because all three scopes reach them),
exactly one shape can arrive here and the slot can say which.

Most code is unaffected. `defineServerMiddleware(...)` with no scope argument
still fits, since an all-scope middleware flows into a single-scope slot, and so
does `defineServerMiddleware<'loader'>(...)`, which is now the precise spelling.
What stops compiling is a `<'page'>` or `<'action'>`-tagged guard reused in one
of these slots:

```
error TS2322: Type 'ServerMiddleware<"page">' is not assignable to
  type 'ServerMiddleware<"loader"> | ClientMiddleware'.
    Type '"loader"' is not assignable to type '"page"'.
```

Both tags were promising something the upgrade never delivered, though not in
the same way. An `<'action'>` guard reads `ctx.action` and `ctx.payload`, which
the upgrade probe never sets, so those reads were already `undefined` at runtime.
A `<'page'>` guard fared better: every field `ServerPageCtx` names (`c`,
`signal`, `location`) is populated by the probe, so the guard ran and read real
values. What it did not get was its own scope tag; it observes `ctx.scope` as
`'loader'`, so any branch keyed on `ctx.scope === 'page'` silently never fired.

Retag to `<'loader'>` if the guard is realtime-only. If it is shared with the
page or action tiers, drop the tag and narrow on `ctx.scope`, because the
all-scope ctx makes `location` optional (the bare-action path has none):

```ts
// before: a page-tagged guard reused on a socket
const requireOrg = defineServerMiddleware<'page'>(async (ctx, next) => {
  if (!ctx.location.pathParams.orgId) return deny(403);
  await next();
});

// after, realtime-only: body unchanged, the loader ctx also has `location`
const requireOrg = defineServerMiddleware<'loader'>(async (ctx, next) => {
  if (!ctx.location.pathParams.orgId) return deny(403);
  await next();
});

// after, shared across tiers
const requireOrg = defineServerMiddleware(async (ctx, next) => {
  if (ctx.scope !== 'action' && !ctx.location.pathParams.orgId) {
    return deny(403);
  }
  await next();
});
```

One behavior worth re-reading while you are in these guards: any guard outcome
denies the upgrade, and a WebSocket handshake cannot follow an HTTP redirect, so
a redirecting guard can only fail closed. The framework warns and names the
socket when that happens, rather than leaving an inexplicable 4403. Use `deny()`
in realtime guards.

### `Middleware` is now a union over the scopes (#351)

`Middleware` is the classifier's output type: what the framework hands back
after deciding, structurally, that a `use` entry is a middleware rather than a
stream observer. It used to read `ServerMiddleware | ClientMiddleware`, and a
bare `ServerMiddleware` defaults to `ServerMiddleware<Scope>`, which means
"handles page, loader **and** action". That was a promise nothing had checked.
Classification proves an entry carries `runs: 'server'` and nothing else; the
scope an entry was authored for leaves no runtime trace. So the type asserted, of
every classified entry, a capability most of them never claimed. `Middleware` now
spells its server half as a union over the individual scopes, and admits a
single-scope `defineServerMiddleware<'loader'>(...)` as readily as an all-scope
one.

By itself that is a widening. What breaks a build is the combination with
`ServerMiddleware` having become contravariant in its scope: a
`ServerMiddleware<'page'>` no longer fits an all-scope slot, and
`AppConfig['use']` and `RouteDef['use']` are all-scope slots. A `Middleware[]`
annotation therefore stops being assignable to either. This is the one line of
the change most likely to reach an app, and it reaches it through an annotation,
not through the middleware itself.

```ts
// before: compiled
const guards: Middleware[] = [auth];
export default defineApp({ use: guards });
defineRoutes([{ path: '/admin', use: guards, view: () => import('./admin.js') }]);

// after: annotate with the slot's own element type
import type { AppUseElement } from 'hono-preact';

const guards: AppUseElement[] = [auth];
export default defineApp({ use: guards });
defineRoutes([{ path: '/admin', use: guards, view: () => import('./admin.js') }]);
```

`AppUseElement[]` fits both tiers when the array is server-only, as a shared
guard list is. An array that also carries client middleware can only sit on a
route node, and its annotation is `RouteUseElement[]` (#359, above).

Dropping the annotation entirely and letting the array infer works just as well.
Either spelling needs the entries themselves to be all-scope, which means
`defineServerMiddleware(...)` written with no scope argument. An entry authored
as `defineServerMiddleware<'page'>(...)` is rejected by both spellings, and
removing the tag is the fix rather than a workaround: a route node's `use` wraps
that route's loaders and actions as well as its render, so a `<'page'>` tag there
was describing a dispatch that does not happen.

If you hand-roll a dispatch over a `Middleware` array, the `fn` call site needs
the same treatment. A union of three single-scope middlewares has a union of
three `fn` signatures, and calling it demands a ctx assignable to all three at
once, which reduces to `never`:

```ts
// after: narrow to the scope you are about to dispatch in
const server = list.filter(
  (m): m is Middleware & ServerMiddleware<'loader'> => m.runs === 'server'
);
for (const m of server) await m.fn(loaderCtx, next);
```

There is no runtime change here. `Middleware` was, and still is, purely a type.

## Breaking: elsewhere

### `next()` resolves with nothing, and `return next()` finally typechecks (#351)

`Next` was `() => Promise<unknown>`. It is now `() => Promise<void>`, and this is
a **runtime** change as well as a type change: the dispatcher no longer resolves
`next()` with the inner handler's value.

The old typing was the sole reason `return next()` did not compile. A middleware
`fn` returns `Promise<void | Outcome>`, and `Promise<unknown>` is not assignable
to that, so the framework rejected the exact spelling its own contract-violation
message prescribes ("Middleware must either: (a) await/return next() to pass
control on, or (b) throw a redirect/deny/render outcome to short-circuit").
Typing the seam `unknown` also published an implementation detail: the inner
value is threaded back to the dispatcher's caller, and nothing in the chain ever
gave it a meaning at this seam.

**Unchanged.** The ordinary spelling and everything built on it:

```ts
export const timing = defineServerMiddleware(async (ctx, next) => {
  const t = Date.now();
  await next();            // still awaits the whole downstream
  console.log(Date.now() - t);
});
```

`try { await next() } finally { … }` still wraps the full downstream, a throw
still unwinds through it, and the value the dispatcher hands back to *its* caller
(your loader's data, your action's result, the page render) is untouched.

**Now compiles that did not.** Pass-through middleware:

```ts
// before: error TS2322 -- Type 'Promise<unknown>' is not assignable to type 'Promise<void | Outcome>'
// now:    fine
export const passthrough = defineServerMiddleware(async (ctx, next) => next());
```

**Silently different.** A middleware that read what `next()` resolved with now
gets `undefined`. Where that value was consumed as `unknown`, the code still
compiles and simply stops matching:

```ts
defineServerMiddleware(async (ctx, next) => {
  const v = await next();
  if (typeof v === 'object' && v !== null && 'rows' in v) {
    audit(v);              // compiled before and still compiles; now never runs
  }
});
```

Two spellings the compiler does catch: a cast, where `(await next()) as Result`
is now TS2352 (`void` to `Result`), and a truthiness test, where
`if (await next())` is now TS1345 ("an expression of type 'void' cannot be tested
for truthiness"). If you were reading that value, take it from where the work
happens instead: the loader or action's own return, or the ctx.

**One trap this avoids opening.** The dispatcher short-circuits when a middleware
*returns* an `Outcome`. Had `return next()` become legal while `next()` still
forwarded the inner value, an inner result that happened to be `Outcome`-shaped
would have been read as a short-circuit. Resolving with nothing is what stops the
newly legal spelling from meaning that, which is why the runtime half ships
alongside the type half. The RPC loader, action, and `call()` paths were never
exposed either way: each deliberately re-throws an `Outcome`-shaped return so it
is translated as an outcome regardless of what the middleware does.

### `LoaderFn` takes a streaming discriminant, so its params generic moved (#351)

`LoaderFn` was an alias for the internal `Loader` union: three call signatures
(`Promise<T>`, `Promise<ReadableStream<T>>`, `AsyncGenerator<T>`) over one
context, with the type parameters `<T, TParams, TSearch>`. It is now a single
signature per form, selected by a `Live` discriminant in second position:

```ts
// before
type LoaderFn<T, TParams = Record<string, string>, TSearch = Record<string, string>> =
  | ((ctx: LoaderCtx<TParams, TSearch>) => Promise<T>)
  | ((ctx: LoaderCtx<TParams, TSearch>) => Promise<ReadableStream<T>>)
  | ((ctx: LoaderCtx<TParams, TSearch>) => AsyncGenerator<T, void, unknown>);

// now
type LoaderFn<T, Live extends boolean = false, TParams = /* standalone */, TSearch = Record<string, string>> =
  Live extends true
    ? (ctx: LoaderCtx<TParams, TSearch>) => AsyncGenerator<T, void, unknown>
    : (ctx: LoaderCtx<TParams, TSearch>) => Promise<T>;
```

The old shape did not compose with the constructor it was named for.
`defineLoader` discriminates its overloads on the return type, and a union of
signatures resolves against neither, so a function annotated `LoaderFn<T>` could
not be handed to `defineLoader` at all. It also defaulted to the **route-bound**
context, so the bare `LoaderFn<T>` promised a `ctx.location` that a standalone
loader never receives. The generics now mirror `LoaderRef<T, Live>`: a
`LoaderFn<T, Live>` is exactly what `defineLoader` takes to give you back a
`LoaderRef<T, Live>`.

The migration is entirely about parameter positions. `Live` took slot two, so
params and search shift right by one, and the default context is now the
standalone one.

```ts
// standalone, single value -- unchanged spelling, and now actually usable
const listMovies: LoaderFn<Movie[]> = async ({ signal }) => fetchMovies(signal);
export const serverLoaders = { default: defineLoader(listMovies) };  // was TS2769

// streaming: the generator arm is no longer folded into the bare form
- const ticks: LoaderFn<number> = async function* () { yield 1; };
+ const ticks: LoaderFn<number, true> = async function* () { yield 1; };

// route-bound: params move from slot two to slot three
- const oneMovie: LoaderFn<Movie, RouteParams<'/movies/:id'>> =
+ const oneMovie: LoaderFn<Movie, false, RouteParams<'/movies/:id'>> =
    async (ctx) => getMovie(ctx.location.pathParams.id);

// bare LoaderFn<T> used to carry `location`; if you read it, name the params
- const f: LoaderFn<Movie> = async (ctx) => getMovie(ctx.location.pathParams.id);
+ const f: LoaderFn<Movie, false, RouteParams<'/movies/:id'>> = async (ctx) => …;
```

Every stale spelling is a compile error, each with a legible message: params in
slot two is `TS2344: Type '{ id: string; }' does not satisfy the constraint
'boolean'`, a generator on the bare form is `TS2322: 'AsyncGenerator<number,
void, unknown>' is missing … from type 'Promise<number>'`, and reading
`ctx.location` off a standalone context is `TS2339: Property 'location' does not
exist on type 'LoaderCtxBase'`.

Spell the params out only when the function actually reads `ctx.location`. A
standalone-typed `LoaderFn` asks less of its context, so
`serverRoute(r).loader(fn)` accepts one too.

The raw `ReadableStream` arm is gone from `LoaderFn`. It was a runtime-only form
the loaders handler pipes to SSE, unreachable through either constructor's public
overloads; it stays on the internal `Loader` union, which is not exported.

## Additions

### `<For>` and `<Show>` (#355)

Two rendering helpers bound to signals, exported from `hono-preact`.

```tsx
<For each={memberIds} by={(id) => id}>
  {(id) => <Cursor member={member(id.value)} />}
</For>

<Show when={session} fallback={<SignIn />}>
  {(user) => <Greeting name={user.name} />}
</Show>
```

`<For>` reconciles rows by key, so a key that survives keeps its DOM and its
component state; each row runs in its own component boundary, so a signal read
inside a row re-renders that row alone. `item` and `index` arrive as per-row
signal cells that stay object-stable while the key survives, which is what lets
a row hand a stable reactive identity to its own subcomponents and effects.

The default key is the item itself. Supply `by` whenever the array holds objects
rebuilt per payload (deserialised loader data, for instance), or every row
remounts on each new array because no two objects are ever `===`.

A function child of `<Show>` receives the narrowed truthy value.

### The deny path is typed end to end (#322)

A denial used to lose most of itself on the way out. Three things changed:

- **Loaders.** The deny envelope carries its `code` now, and a denied loader
  throws the new `LoaderDenyError` (`status`, `code?`, `data?`), which reaches
  `errorFallback` like any loader error. Schema failures still arrive as
  `LoaderValidationError`.
- **Actions.** `mutate()` reports a denial as its own arm rather than a
  flattened `Error` (see the breaking table), carrying the new public
  `DenyRecord`.
- **Deny data is inferred from your guards.** `deny()` is generic, and a guard
  written with the new scope-argument spelling
  `defineServerMiddleware('action', fn)` carries its deny-data type through
  `defineAction`'s `use` array onto the action, so `deny.data` arrives typed at
  the call site. The older `defineServerMiddleware<'action'>(fn)` spelling
  cannot infer it (TypeScript has no partial type-argument inference) and keeps
  `unknown`.

Two honest limits: a guard attached at the route or app tier is invisible to
this inference, so its denial arrives typed as the action's own union, which it
may not match; and, exactly like `TResult`, the declared type is a contract
rather than a validation at the wire boundary. A framework validation failure
travels in a separate `issues` field, so it can never masquerade as your guard's
`data`.

### `NavLink` accepts anchor attributes (#350)

`NavLinkProps` derived from `JSX.HTMLAttributes<HTMLAnchorElement>`, the generic
element attributes, which do not carry the anchor-only ones. `target`, `rel`,
`download`, `ping`, `hreflang` and `referrerpolicy` were rejected by the compiler
on a component that spreads unrecognized props straight onto its `<a>`, and whose
own click gate already reads `a.target` and the `download` attribute to decide
whether to soft-navigate. The props the runtime depends on were unspellable by a
caller.

The type is now `JSX.AnchorHTMLAttributes<HTMLAnchorElement>`.

```tsx
// before: error TS2322, "Property 'target' does not exist"
// after: compiles
<NavLink href="/spec.pdf" target="_blank" rel="noreferrer" download>
  Download the spec
</NavLink>
```

This is strictly additive. The two shapes are mutually assignable, every prop
that typechecked before still typechecks, and forwarding a `NavLinkProps` value
on to a plain `<a>` is unchanged. There is nothing to migrate; it only stops the
compiler refusing markup the component already handled.

## Correctness and hardening

Four failures that were silent are not any more, plus one bundle-size change.
None of them needs anything from you beyond knowing they exist.

- **A malformed `use` entry no longer disappears (#321).** Entries were sorted
  by exclusion, so anything that was not recognisably middleware became an
  observer, and observers do not gate a request. A broken auth guard could sit
  in a chain doing nothing. Entries are validated against the whole contract
  when the chain is composed, and a bad one fails closed through the normal
  error envelope instead of passing traffic.
- **`export class` no longer bypasses the `.server.ts` whitelist (#335).** The
  build-time check collected exports from two declaration kinds, so a class (or
  an enum) slipped past it entirely and the file reported clean. The check is
  exhaustive now, and an unhandled declaration kind fails loudly rather than
  silently passing. The separate import-site gate always held, so this was
  defense in depth rather than an open door.
- **A custom Vite `base` fails the build (#323).** Route CSS hrefs are emitted
  root-relative, so a configured `base` produced a page whose stylesheets all
  404 with no diagnostic anywhere. It is now a config-time error naming the
  limitation. Real `base` support can follow if anyone needs it.
- **The `eventStream` queue is capped (#325).** See the breaking table: 128
  payloads, drop-newest, one warning naming the topic. `createCache` also warns
  once when it falls back to a process-global store because no request store is
  present, which is a correctness cliff nobody was told about.
And the size change: **framework error prose stays out of the production client
bundle (#338).** The long remediation messages are gated behind a dev check, so
they no longer ship to the browser. The messages themselves are unchanged in
development.

## Why these broke now

None of these are redesigns, and none of them are new opinions about how
middleware should work. The dispatch is untouched; it was already correct.

No CI step had ever typechecked a test file. `pnpm typecheck` runs against the
emitting `tsconfig.json`, which excludes `src/**/__tests__/**` (and has to, or
tests would ship to npm); `pnpm test` runs vitest, which strips types without
checking them; `pnpm test:types` only covers `*.test-d.ts`. Three gates, three
different reasons to miss the same thing. Turning the tests on (#350) surfaced
390 accumulated type errors and, with them, the source defects fixed here (#351).

The reason the scope tags had never enforced anything is `ServerCtx<S>`. Written
as a conditional chain with `S` in the check position, both of the compiler's
variance probes fall through to the same branch, so `ServerMiddleware<S>`
measured bivariant and every `<'page'>` / `<'loader'>` / `<'action'>` tag in the
codebase was an unchecked comment. Once the alias measures contravariant, the
tags bind, and two slots that had been lying about their scope for several
releases stop compiling. That is the whole cut.

## Upgrade

Bump the dependencies and reinstall:

```jsonc
// package.json
"hono-preact": "^0.13.0",
"hono-preact-ui": "^0.4.0",  // if you use it
"preact": ">=10.25.0"
```

Then run `tsc`. Most of the work is mechanical and the compiler will lead you
through it. Four things it will not tell you:

1. **The signal hazards.** A truthiness gate on `useActionResult()` or
   `useRoom().self`, a dependency array holding a now stable signal reference, a
   sink typed `unknown`, or a signal that reaches string or JSON coercion. All
   four compile. `2026-07-27-signals-migration-release-notes.md` has the greps.
2. **If any middleware read `next()`'s resolved value, that value is now
   `undefined`.** Search your middleware for `await next()` used as an
   expression rather than a statement. Take the value from the loader or action
   that produces it instead.
3. **When you drop a `<'page'>` tag from an app-level or route-level guard, the
   guard now sees the loader and action contexts too.** That is what it was
   already doing at runtime, so re-read the body once with that in mind, and
   remember that `ctx.location` is optional off the all-scope context. Absent is
   not "unrestricted": fail closed.
4. **If you pass handlers on a `render` vnode to a `hono-preact-ui` part, they
   fire now.** They were being dropped. Anything you wrote there expecting it to
   be inert is live; anything you wrote expecting it to work finally does.

Then exercise the app once with both consoles in view. Three of this release's
new warnings are worth seeing before production does, and they do not all land
in the same place: the non-focusable-trigger warning is a browser warning, while
the `eventStream` cap and the `createCache` fallback are server-side and appear
in your server or worker log.
