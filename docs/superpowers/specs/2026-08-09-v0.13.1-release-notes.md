# hono-preact v0.13.1: release notes

**Released:** 2026-08-09

A correctness patch for three server-side rendering failures introduced in
v0.13.0. No API changes, no behavior changes beyond the pages that were
returning 500. Upgrade if you are on 0.13.0.

Every one of these is a module-graph or bundling-order fault, which is why a
fully green test suite shipped alongside them: they cannot reproduce under a
test runner's own module resolution. Only booting a real server and requesting
a page exposes them, which is now a gate in CI.

## Dev server returned 500 on every page (Node adapter)

Any app using `nodeAdapter()` returned a 500 with `Error: Cycle detected` for
every page it rendered in `vite dev`. Applications scaffolded by
`create-hono-preact --adapter=node` were affected from the first run. Production
builds were never affected.

Vite loads `vite.config.ts` by importing it into the Node process, so
`hono-preact/vite` was evaluated there. It imported four string constants from a
barrel that also re-exports the loader runtime, and as of v0.13.0 that runtime
reaches `@preact/signals`. Signals therefore initialized once at config-load
time and patched Preact's `options` in the Node process. Vite's SSR module
runner then loaded a second copy which patched the same shared `options`. With
two render hooks installed, a single component render started the same internal
effect twice, and signals correctly refused.

The Vite plugin now imports its constants from a dedicated module that holds
only constants and imports nothing, so build-time code no longer reaches the
runtime at all.

## Dev server returned 500 on every route (Cloudflare adapter)

The same `Cycle detected` failure, reached a different way. `preact/devtools` is
injected by a transform rather than written in any source file, so Vite's
dependency scan could not find it and discovered it partway through startup
instead. The resulting re-optimization left two copies of `@preact/signals`
live at once, with the same two-render-hooks consequence as above.

`preact/devtools` is now pre-bundled explicitly, which is the only way to
pre-bundle something the scan cannot see.

## Production 500 on routes with no loader

A route whose page component calls a signals-backed hook, such as
`useFormStatus` or `useActionResult`, but which declares no loader, returned a
500 from the built server. The page's HTML rendered completely, so the failure
appeared only in the status code and in server logs, as
`Cannot read properties of undefined (reading '__$f')`.

Routes with a loader were unaffected, because the loader module pulled
`@preact/signals` into the graph early enough. Without one, nothing did, and
`@preact/signals` was first evaluated partway through rendering, after
`preact-render-to-string` had already captured the render hooks it would use for
the whole page. The framework's SSR entry now initializes signals up front.

## Also in this release

`@preact/signals` moves to 2.11.0 and `preact-render-to-string` to 6.7.0. Both
were already permitted by the existing version ranges. Neither is required by
the fixes above.

## Upgrading

`hono-preact@0.13.1` is a drop-in replacement for `0.13.0`. Projects scaffolded
with `create-hono-preact` pin `^0.13.0`, so a fresh install or
`pnpm update hono-preact` picks up the fixes with no code changes.

`create-hono-preact@0.13.1` is a version-parity release. Its templates and
generated output are unchanged from 0.13.0.

`hono-preact-ui` is unaffected and stays at 0.4.0.
