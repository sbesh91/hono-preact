# hono-preact-ui v0.4.0: release notes

**Released:** 2026-08-09

One behavior change, and it lands on a public surface: a handler you pass on a
`render` vnode now runs. Until this release it was silently dropped. Nothing was
added, removed, or renamed; `index.ts` is byte-identical to
`hono-preact-ui@0.3.0`, so the published export surface is unchanged.

Ships alongside framework `v0.13.0`, on its own line and tag namespace.

## Versions

| Package | From | To | Why |
|---|---|---|---|
| `hono-preact-ui` | 0.3.0 | **0.4.0** | render-prop handlers compose instead of being dropped |

## Behavior change

### Render-prop handlers compose, user first (#332)

Every part that takes a `render` prop merges your props with its own. For a
colliding key the part's prop used to win outright:

```js
// before, in mergeProps
out[key] = framework[key];
```

For `class` and `ref` that was already special-cased and correct. For an event
handler it was silently destructive:

```tsx
<Tooltip.Trigger render={<button onClick={mine} />}>Help</Tooltip.Trigger>
```

`mine` never ran. Not "ran and was overridden": it was overwritten before the
vnode was cloned, so nothing called it. The part's own `onClick` was the only
survivor.

Now, when both sides hold a function and the key looks like an event handler
(`/^on[A-Z]/`), the two are composed and **yours runs first**:

```js
out[key] = composeHandlers(user, framework);
```

That ordering matches how the parts already chain handlers you pass as ordinary
props: they call `onClick?.(event)` before doing their own work. The render-prop
path was the odd one out.

**What to check when you upgrade.** Search your app for handlers passed inside a
`render` vnode. Any of them that appeared to do nothing now fire on every
relevant event. Two consequences worth naming:

- A handler you added, saw no effect from, and left in place is now live.
- Composition is unconditional: calling `preventDefault()` in your handler does
  not stop the part's own handler from running, exactly as it does not for a
  handler passed as a plain prop. If you need to suppress a part's behavior, use
  the part's own API rather than a veto from a handler.

Non-handler prop collisions are unchanged: the part's prop still wins. Only
`on[A-Z]*` keys where **both** sides hold a function are composed.

### A dev-only warning for non-focusable triggers (#332)

A trigger rendered onto an element that cannot receive focus loses keyboard
access, silently. In development the library now warns when a `render` override
resolves to such an element:

```tsx
// warns: a span cannot be focused, so this trigger is not keyboard reachable
<Tooltip.Trigger render={<span />}>Help</Tooltip.Trigger>
```

The check runs only when you supply a `render` override, and only in
development; it is compiled out of production builds. An author-set `tabindex`
counts as focusable, **including `tabindex="-1"`**, so the library's own roving
tabindex patterns (menu items, listbox options) do not warn. `<a>` without
`href` and disabled controls are correctly treated as non-focusable.

The fix is either an element that is focusable by default (`button`, `a[href]`)
or an explicit `tabindex` if you are managing focus yourself.

## Everything else

No other behavior changed. The rest of the diff since `hono-preact-ui@0.3.0` is
housekeeping: `merge-refs.ts` exports its `AnyRef` type so `render-element.ts`
can name it without a cast (module-internal; it is not in the package's
`exports`), a `types.d.ts` declares `import.meta.env` so typechecking does not
require pulling in `vite/client`, and the test files gained type annotations
plus a `tsconfig.test.json` and a `typecheck:tests` script, from the
framework-wide work that put test files under `tsc` for the first time.

## Upgrade

```jsonc
"hono-preact-ui": "^0.4.0"
```

There is nothing to migrate. Read the behavior change above, run the app once
with the dev console open, and check any handler you had passed through a
`render` vnode.
