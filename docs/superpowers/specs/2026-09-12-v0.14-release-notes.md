# hono-preact v0.14.0

**Released:** 2026-09-12

The largest cut since v0.13. Server-published **session channels** are the
headline: a typed value a server middleware publishes on each round-trip and its
paired client middleware reads, so a client guard can act on a real server
answer instead of guessing. Around that sit the two ergonomics tracks (#318,
#319, #320), the loader-state and navigation batch (`match()`, split
`invalidate`, a two-parameter `.View` render, `NavLink` prefetch),
build-emitted assets served in dev (`honoPreact({ assets })`), and the type
migration that makes the packages compile against both Preact majors.

Six breaking type changes plus a `preact` peer-minimum bump, all mechanical.
The two with real migration cost are the `.View` render signature and the
`invalidate` option; budget a grep-and-edit pass for each.

## Breaking: `.View` render callbacks take `(state, props)`

The highest-cost migration in this release. A `.View` render function used to
receive one flattened object that intersected the loader state with the
component's own props; it now receives the loader state first and the caller's
props second.

```tsx
// before
const Movie = movieLoader.View(({ status, data, heading }) => ...);

// after
const Movie = movieLoader.View((state, props) => ...);
```

The flattened form made a caller prop named `data`, `status`, or `error` alias
into the loader state, silently shadowing it. Two parameters make the two
sources distinct, which is also what lets `props` keep the component's own
generic type.

Pairs well with `match()` (below), which pattern-matches the state argument
without a `switch`.

## Breaking: `invalidate` takes `{ clear }` / `{ refetchActive }`

The `invalidate` option on `useAction` and `<Form>` no longer accepts
`'auto'`, `false`, or a bare array of loader refs. The replacement is an
object with two independent fields, because the old spellings conflated
clearing a cache with re-running the active loader:

```ts
type InvalidateInput = {
  clear?: ReadonlyArray<AnyLoaderRef>;
  refetchActive?: boolean;
};
```

`refetchActive` defaults to `true` when the active loader appears in `clear`,
and `false` otherwise, so the common case stays a one-liner.

```ts
// before
useAction(save, { invalidate: 'auto' });
useAction(save, { invalidate: [listLoader] });
useAction(save, { invalidate: false });

// after
useAction(save, { invalidate: { refetchActive: true } });
useAction(save, { invalidate: { clear: [listLoader] } });
useAction(save); // omit it
```

TypeScript rejects the old spellings outright. Because an untyped JavaScript
caller would otherwise pass one silently and get no invalidation at all, a
dev-and-SSR-only throw names the old spelling and the replacement; it folds out
of a production build.

## Breaking: `MutateResult` is now five arms, discriminated by `kind`

This is the **second consecutive breaking change** to this type. v0.13 split
`mutate()`'s result into three arms so a denial and a thrown error could be
handled separately from success; v0.14 regularizes the discriminant so all
arms share one field, fixes a case v0.13 left unresolved (a same-origin
redirect never settled the promise at all), and splits cancellation out of
the generic error arm so an awaiting caller can tell "the mutation failed"
apart from "I cancelled it."

```ts
type MutateResult<TResult, TDenyData> =
  | { ok: true; kind: 'success'; data: Serialize<TResult> | undefined }
  | { ok: true; kind: 'navigated' }
  | { ok: false; kind: 'deny'; deny: DenyRecord<TDenyData> }
  | { ok: false; kind: 'aborted'; error: Error }
  | { ok: false; kind: 'error'; error: Error };
```

**What changed:**

- The success arm now carries `kind: 'success'` alongside `ok: true`, so
  `kind` is a uniform discriminant across all five arms instead of only the
  failure arms.
- A new `{ ok: true, kind: 'navigated' }` arm settles when the action
  redirects to a same-origin destination. Previously that `await mutate(...)`
  never resolved. `onSuccess` does not fire for this arm (there is no result
  to hand it), declared loaders are **not** invalidated, and `pending` clears.
  The redirect is a full document load, so the destination gets a fresh SSR
  payload and fresh in-memory loader caches; a client-side invalidation could
  not affect it and would race the document teardown.
  Because navigation may already have unmounted the caller, code after the
  `await` must not assume the component is still mounted.
- A new `{ ok: false, kind: 'aborted', error }` arm settles when the
  mutation was cancelled (unmount or a caller-supplied `signal`), previously
  indistinguishable from `kind: 'error'` except by sniffing
  `err.name === 'AbortError'`. `onError` still fires on abort, so an
  optimistic wrapper still reverts its pending entry, but the hook's `error`
  state is deliberately not set: a cancellation is not a rendered failure. A
  deny the server had already decided before the caller aborted still
  resolves with `kind: 'deny'`, never `'aborted'`.

**Migration:**

```ts
// before
const r = await mutate(payload);
if (r.ok) use(r.data);

// after
const r = await mutate(payload);
if (r.ok && r.kind === 'success') use(r.data);
```

An exhaustive `switch (r.kind)` over `'success' | 'navigated' | 'deny' |
'aborted' | 'error'` is the more robust form if your callback needs to react
to a redirect or a cancellation explicitly.

If you were previously distinguishing a cancellation from a real failure by
checking `err.name === 'AbortError'` on the returned error, an awaiting
caller can now check `r.kind === 'aborted'` directly instead:

```ts
// before
const r = await mutate(payload);
if (!r.ok && r.kind === 'error' && r.error.name !== 'AbortError') {
  showToast(r.error.message);
}

// after
const r = await mutate(payload);
if (!r.ok && r.kind === 'error') {
  showToast(r.error.message);
}
```

This only helps awaiting callers. `onError` still receives a plain `Error`,
not the arm, so an `onError` handler that wants to skip cancellations still
needs the `err.name === 'AbortError'` check; the new arm does not change what
`onError` is passed.

**Verification note.** This break produced zero in-repo fallout, checked
consumer by consumer: the repo's only `.ok`-narrowing consumer never reads
`.data`, so it did not need the added `kind === 'success'` check to keep
working, and the repo's own demo app never exercises the `navigated` arm in
the first place. That is not evidence the migration is smooth in practice; it
means the change was not exercised against a real consumer here. The
migration burden falls entirely on external callers of `mutate()`.

## Breaking: `defineLoader`'s `params` option is now `cacheKeyParams`

Mechanical rename. `paramsSchema` is unchanged; it validates and coerces path
params and is unrelated to this option, which lists the search-param cache
dependencies a loader's client-side cache key includes.

```ts
// before
serverRoute('/movies').loader(fn, { params: ['genre'] });

// after
serverRoute('/movies').loader(fn, { cacheKeyParams: ['genre'] });
```

This option is route-bound only. A bare `defineLoader(fn, opts)` has never
accepted it (or the old `params`), so only `serverRoute(...).loader(...)` call
sites are affected.

The old name collided in a reader's head with `paramsSchema` despite naming
an unrelated concern (cache-key dependencies, not param validation). Rename
before the ambiguous name fossilizes into more call sites.

The rename also reaches the exported `LoaderRef` type: the returned ref's
`params` property is now `cacheKeyParams`. Code reading `myLoader.params`
directly (not just the `defineLoader` option) needs the same rename.

## Breaking: `RouteBinder.room`'s `Data` generic default is now `undefined`

`RouteBinder.room<Name, Payload, State, Data = undefined>` now defaults
`Data` to `undefined`, matching `defineRoom`'s own default. Previously the
two constructors disagreed: `defineRoom` already defaulted to `undefined`,
`RouteBinder.room` still defaulted to the wider `Record<string, unknown>`.

This affects only code that relied on the wider default without naming
`Data` explicitly (an untyped room payload read as `Record<string, unknown>`
where it is now `undefined`). If you were relying on that default, name
`Data` explicitly at the call site:

```ts
route.room<'cursors', Payload, void, Record<string, unknown>>(channel, handler);
```

## Breaking: `serverEntryPlugin`'s generated-path options are gone

`serverEntryPlugin` (an advanced internal exported from `hono-preact/vite`)
no longer takes `coreAppPath` and `entryWrapperPath`. It derives both from the
resolved Vite root itself, inside the `config` hook where the root first
becomes knowable. An optional `rootRef` replaces them, and omitting it is
correct for a standalone call: pass one only when another plugin must read the
same resolved root.

This affects only code that calls `serverEntryPlugin` directly. Apps using
`honoPreact()` see no change, and because `rootRef` is optional, a caller that
passed neither removed option still compiles.

The paths were previously computed from `process.cwd()` when `honoPreact()` was
called, before any Vite hook runs. Under a custom Vite `root` that wrote the
generated core-app and entry-wrapper modules into the wrong tree.

Related: the three path fields on `HonoPreactAdapterContext` (`root`,
`coreAppModuleId`, `entryWrapperId`) are now lazily resolved. Their declared
type is unchanged, but a third-party adapter must read them from inside a
plugin hook rather than from the body of `vitePlugins()`, where the root is not
yet known.

## Breaking: the `preact` peer minimum is now `>=10.28.0`

`hono-preact`, `@hono-preact/iso`, and `hono-preact-ui` now require Preact
**10.28.0** or newer, up from `>=10.25.0` (framework) and `>=10.11.0` (ui).
`@hono-preact/server` is unchanged at `>=10.0.0`.

Nothing about the framework's runtime behavior needs 10.28. The bump exists
because `hono-preact-ui`'s public types now import `HTMLAttributes`,
`CSSProperties` and `TargetedMouseEvent` from the `preact` package root rather
than from the `JSX` namespace. Preact re-exports those from the root as of
10.28.0; on 10.27 and earlier they are reachable only as `JSX.*`, so the
packages' own `.d.ts` files would not resolve. (The framework's element props
take the other half of the migration: they derive from
`JSX.IntrinsicElements[tag]`, which is stable across both majors.)

This is also forward-preparation: Preact 11 removes those types from the `JSX`
namespace entirely, and the root-import spelling is the one that works on both
majors. It is not an adoption of Preact 11; see the readiness tracker for the
`preact-iso` blocker that still gates that.

Nothing changes at your call sites. If you are on Preact 10.28 or newer (10.29
has been current since well before this release), there is nothing to do.

### `Form` props are wider than they were

A side effect worth knowing, because it turns former type errors into valid
code rather than the reverse. `FormProps` now derives from
`JSX.IntrinsicElements['form']` instead of the generic
`JSX.HTMLAttributes<HTMLFormElement>`, so form-specific props that were
previously unspellable now typecheck:

```tsx
<Form action={save} novalidate target="_blank" autocomplete="off" />
```

`NavLinkProps` was re-derived in the same pass, from
`JSX.AnchorHTMLAttributes<HTMLAnchorElement>` to `JSX.IntrinsicElements['a']`,
but its accepted props are unchanged: anchor-specific props like `rel` and
`ping` were already spellable. That change preserves Preact 11's per-element
`role` narrowing rather than widening anything.

No existing code breaks; the accepted set only grew.

## Additions

### Session channels: a typed hint from the server guard to the client guard

A client-side guard has no way to know what the server decided. It either waits
for an RPC round-trip to find out, or it guesses from state it keeps itself and
drifts. `defineSessionChannel()` gives the two tiers one typed value to agree
on: the server publishes it on every round-trip, the client reads what the last
round-trip published.

```ts
import { defineSessionChannel, defineServerMiddleware, defineClientMiddleware, redirect } from 'hono-preact';

export const session = defineSessionChannel<{ signedIn: boolean }>();

export const publishSession = defineServerMiddleware(async (ctx, next) => {
  session.publish(ctx, { signedIn: Boolean(await currentUser(ctx.c)) });
  await next();
});

const requireSessionClient = defineClientMiddleware(async (ctx, next) => {
  const hint = session.read(ctx);
  if (hint !== undefined && !hint.signedIn) throw redirect('/login');
  await next();
});
```

`SessionChannel<T>` carries `publish(ctx, value)` (server tier only: the `ctx`
parameter is what keeps client code from reaching it), `read(ctx)` (client
tier), and a `__channelId` used for the wire keying.

**The three-state read is the contract.** `read()` returns `undefined` when no
round-trip has published on this channel, and that is UNKNOWN, not "denied". A
guard should defer on `undefined` and let the server (which is always the
authority) decide, rather than bouncing a visitor who is genuinely signed in.
Clearing a channel is an explicit publish of a falsy value, never an omission:
a response that says nothing about a channel leaves it as it was.

**Payloads are flat and public.** `ChannelPayload` admits a primitive, an array
of primitives, or a one-level record of those. Everything published ships to the
browser, so publish a decision (`{ signedIn: true }`, a role, a plan tier),
never a token. A dev-only warning fires past 256 encoded bytes.

**Wire format.** Published values travel as an `X-HP-Channels` response header
on loader, action and streamed-loader responses, and as an inline
`window.__HP_CHANNELS__` bootstrap on the SSR document.

**Caching.** A document that carries a published snapshot is per-visitor, so a
shared cache must not store it. On a normal document the framework sets
`Cache-Control: private, no-store` **only when your own middleware has not
already set one**: if you set a `Cache-Control`, yours stands and the caching
decision stays yours. A streamed document is stricter: it builds its own
headers, so a snapshot forces `private, no-store, no-transform` whether or not
you set one. If you want to own caching on a streaming page, do not publish on
it.

**Declare the channel outside a `.server.*` module.** The Vite plugin injects
the cross-bundle id at the `defineSessionChannel()` call site in modules that
ship to both tiers. A channel declared inside a `.server.*` module never gets a
matching id on the client, so `read()` always returns `undefined` without
throwing. A dev-only warning names this case.

Full documentation: `/docs/session-channels`.

### `match()` for status-first loader state

```ts
import { match } from 'hono-preact';

const Movie = movieLoader.View((state) =>
  match(state, {
    loading: () => <Spinner />,
    revalidating: ({ data }) => <Card movie={data} dim />,
    success: ({ data }) => <Card movie={data} />,
    error: ({ error }) => <Failed message={error.message} />,
  })
);
```

Exhaustive by default: a missing arm is a compile error. Supplying a `_`
catch-all opts into a partial map instead. A JavaScript caller that reaches an
unhandled status gets a thrown error naming the status rather than `undefined`.

### `NavLink` prefetch

```tsx
<NavLink href="/movies" prefetch="hover" prefetchLoaders={movieListLoader} />
```

`prefetch` takes `'hover'` (warms on hover intent, and immediately on focus so
keyboard users get the same warming), `'visible'` (warms when the link enters
the viewport), or `false`. It does nothing without `prefetchLoaders`, which
takes one loader ref or an array.

The prefetch machinery loads behind a dynamic import, so a route that only ever
renders plain `NavLink`s does not ship it.

### `honoPreact({ assets })`: build-emitted files, served in dev

Generated files that belong to the client build (an `llms.txt`, a generated
feed, a manifest) can now come from one thunk that both halves use, instead of a
build-time emit plus a hand-written dev route that drifts from it.

```ts
honoPreact({
  assets: {
    'llms.txt': () => renderLlmsTxt(),
  },
});
```

Keyed by output file name relative to the client out dir, so `'llms.txt'` serves
at `/llms.txt`. The thunk runs once during the build and per request in dev,
which is what makes a dev edit show up without a restart. A key with a leading
slash, a `.`/`..` segment, a Hono pattern character, or an empty name throws at
config time rather than producing a file nobody can fetch.

Adds `ClientAssets` and `ClientAssetSource` to the `hono-preact/vite` exports,
and a `mrmime` runtime dependency for content-type lookup. Two content types
shift with it: `.xml` is now `text/xml`, and `.json` no longer carries a
`charset` parameter.

**Adapter authors:** `HonoPreactAdapterContext` gains a required
`assetNames: readonly string[]`. It is the one field exempt from the
lazy-resolution rule described above, because the adapter needs the names while
building its route table. A third-party adapter that constructs this interface
needs the new field.


### `buildPath` accepts `string[]` for rest params

For a rest param (`:name*` / `:name+`), `buildPath` now accepts a `string[]`
in addition to a plain `string`, and builds real slash-separated segments:

```ts
buildPath('/docs/:slug+', { slug: ['a', 'b'] }); // '/docs/a/b'
```

Each array entry is encoded individually and joined with `/`. A plain
`string` is unchanged: it is still encoded whole, so embedded `/` characters
become `%2F` rather than additional segments. This closes the gap where a
multi-segment wildcard path (e.g. a nested docs slug) could not be built
without hand-assembling the URL.

The type this widens (`BuildParams`, the params object `buildPath` accepts)
is deliberately separate from `RouteParams` (what `useParams` and a route
match return): a live matched param off the router is always a single
string, so `RouteParams` was not widened, only the type `buildPath` accepts
when constructing a URL.

### Two new warnings

Both fire in development and during any SSR render, including a **production**
SSR render, where they land on the server console rather than the browser one.
Only the production browser path is unchanged.

- **`useParams` warns on no-match.** `useParams(route)` requires the named
  route to be active, or an ancestor of the active route (a layout or nested
  leaf reading a param a descendant route also matches); when neither holds,
  the object it returns does not have the shape it projects. Dev builds now
  warn once per mismatched route rather than asserting or failing silently.
  Reach for `useRouteMatch(route)` when the route may legitimately not be
  active or an ancestor: it returns the match or `null` instead of a
  mis-shaped object. The route-match work only runs inside the dev/SSR
  check, so a production render pays nothing extra for it.
- **Route registration warns when a leaf view lacks `definePage`.** A leaf
  `view` registered without `definePage` silently loses its route error
  boundary. Dev builds now warn about this, but only when that route's lazy
  `view` thunk actually resolves, which happens on the route's first visit,
  not at registration time. A registered route that is never visited during a
  dev session never warns, so a clean console during development is not proof
  every leaf view uses `definePage`.

### The built Node server runs from any working directory

`nodeAdapter()`'s built entry resolves its client build relative to its own
module location rather than the process working directory, so
`node dist/server/server-entry.js` serves `/static/*` and reads its preload
manifest correctly from any cwd: a systemd unit with no `WorkingDirectory`, a
container with a different `WORKDIR`, or a script run from a repo root.

### `nodeAdapter({ devSsrInclude })`

The dev server hands `/@…` and `/node_modules/…` requests to Vite, which owns
its HMR client and module graph. An app route that starts the same way, such as
a `/@:username` profile page, would otherwise never reach SSR in dev even
though it works in production. List it to force SSR:

```ts
nodeAdapter({ devSsrInclude: [/^\/@(?!vite\/|id\/|fs\/)[^/]+$/] });
```

A string matches by prefix and a RegExp by `test()`, both against the path with
any query string removed. Vite's own endpoints (`/@vite/`, `/@id/`, `/@fs/`,
`/@react-refresh`) always reach Vite regardless of the patterns given here, so
this option cannot break HMR or module loading.

It also overrides the project-file pass-through described under Fixes below, for
the rarer case of an app route whose path collides with a real file on disk.

## Fixes

### Node-adapter apps hydrate under `vite dev` again

No app on the Node adapter hydrated in development. The client entry statically
imports `/src/routes.ts`, the dev middleware answered that request from the SSR
app instead of handing it to Vite, and the browser rejected the module on strict
MIME checking, so the entire client graph never executed. Pages rendered from
SSR and were inert: no interactivity, no client navigation.

The dev middleware now passes a request through to Vite when it names a real
file inside the project root or publicDir. Existence is the discriminator rather
than an extension allowlist, which cannot be right in both directions: too
narrow misses imported assets, too wide swallows app routes that have no file on
disk (`/llms.txt`). Paths that escape the root are never probed and never
claimed, and `devSsrInclude` overrides the pass-through for an app route that
genuinely collides with a file.

Apps on the Cloudflare adapter were never affected. This predates v0.13 and is
not a regression in it.

### A nested layout reads its own params and an absolute path

Two observable changes for a layout component:

- A layout that legitimately declares a rest param (`:rest`, or `0`) no longer
  has that param dropped. A fail-open guard filtered layout params against the
  layout's own relative pattern, which discarded ancestor params.
- `location.path` inside a nested layout is now the absolute path
  (`/org/acme/team/t9`) rather than the relative fragment (`/team/t9`). Code
  reading a layout's `location.path` sees a different string; that string is now
  the one the URL actually shows.

### `useSocket` params and `useRoom` keys are order-independent

Both serialize their key object with sorted keys now. A re-render that produced
the same params in a different literal order previously looked like a different
socket: the connection was torn down and reopened, dropping in-flight frames and
presence. The query value changes shape on the wire; the server parses it as
JSON, so key order was never part of the contract and no server-side change is
needed.

### Loader-RPC location params are validated per value

A non-string value under any `pathParams` / `searchParams` key now denies the
whole payload instead of being passed along. Every downstream guard reads those
records as `Record<string, string>`, so a single non-string value made that type
a lie for the rest of the chain. A client sending one now gets a denial.

### `create-hono-preact` accepts a git-initialized directory

`.git` and `.gitkeep` no longer count as occupying a target directory, so
`git init` (or `gh repo clone`) followed by `npm create hono-preact@latest` in
place now works instead of refusing a "non-empty" directory.

The bundled agent guidance under `agents/skills/` was also rewritten, with its
snippets compiled against the real distribution. If you scaffolded on 0.13 and
diff that directory against a fresh 0.14 scaffold, expect churn there.

### Docs: the no-flash claim for hand-split route CSS is scoped to production

The styling guide promised no flash of unstyled content for hand-split route
stylesheets. That is true of a production build, where the sheet is a `<link>`
in the document head, and false under `vite dev`, where the sheet arrives with
the route's JavaScript and flashes in. The guide now says so. Behavior
unchanged; the published promise was wrong.

### The session-channel client store ships only when a channel is declared

An app that never calls `defineSessionChannel()` no longer pays for the channel
store, the wire decoder or the document hydrate. The always-loaded floor is back
to its pre-channel size (8,249 B gzip, down from 8,412 B).

Declaring a channel installs the store, which is also when the store seeds from
the SSR bootstrap. Nothing changes for an app that declares one, with one
deliberate exception: a channel declared inside a lazily-loaded route chunk
starts empty if a loader or action round-trip completed before that chunk
evaluated, rather than seeding from a bootstrap that round-trip may have
superseded. An empty channel reads as `undefined`, which the client-guard
contract already treats as UNKNOWN and defers to the server verdict on. Declare
channels in a module the entry reaches to avoid the case entirely.


### `useAction` callback parameters infer without `onMutate`

`onSuccess: (data) => ...` and `onError: (err) => ...` are typed now whether or
not the call passes `onMutate`. Previously the options type was a single union
whose two arms differed in callback arity, which left TypeScript no contextual
signature to resolve against, so those parameters came through as implicit
`any` (a compile error under `noImplicitAny`) unless `onMutate` was present.

Existing hand annotations (`onError: (err: Error) => ...`) stay valid; they are
simply no longer needed. `useAction` and `ActionRef.useAction` are overloaded to
make this work, so a value explicitly typed as `typeof useAction` now carries an
overload set rather than one signature.

## Upgrade

Bump the dependency and reinstall:

```jsonc
// package.json
"hono-preact": "^0.14.0",
"hono-preact-ui": "^0.5.0"
```

Then run `tsc`. Raise your own `preact` dependency to `^10.28.0` if it is pinned
lower. Every break is mechanical, in rough order of effort:

1. **`.View` render callbacks.** Grep for `.View(` and change each render
   function from one flattened parameter to `(state, props)`. A call site that
   destructured `{ data }` becomes `(state) => ...` reading `state.data`, or use
   `match(state, { ... })`. This is the one to do first; the compiler finds
   every site.
2. **`invalidate`.** Grep for `invalidate:` on `useAction` and `<Form>`.
   `'auto'` becomes `{ refetchActive: true }`, a bare array becomes
   `{ clear: [...] }`, and `false` means omit the option.
3. **`mutate()` results.** Grep for `mutate(` call sites that check `result.ok`
   and read `.data`; add `&& result.kind === 'success'`, or switch on `kind`.
4. **The loader `params` option.** Grep for `.loader(` calls on a
   `serverRoute` binder that pass `params:` and rename the option to
   `cacheKeyParams`. Also rename `.params` reads on the `LoaderRef` the call
   returns. A bare `defineLoader` never accepted the option, so it is
   unaffected.
5. **`RouteBinder.room`.** Name `Data` explicitly at any call site that relied
   on the old `Record<string, unknown>` default.
6. **`serverEntryPlugin`.** Drop `coreAppPath` and `entryWrapperPath` from
   direct calls. Apps using `honoPreact()` have none.

7. **Third-party adapters.** Add `assetNames: readonly string[]` to your
   `HonoPreactAdapterContext`, and move reads of `ctx.root`,
   `ctx.coreAppModuleId` and `ctx.entryWrapperId` out of the `vitePlugins()`
   body into a plugin hook or `wrapEntry()`: those three are lazily resolved
   now and are only correct once a `config` hook has run. `assetNames` is the
   one field exempt from that rule.

If you put a shared cache or CDN in front of the app and you adopt session
channels, read the caching rule above before publishing on a cacheable page.

No signals or middleware-scope changes in this release, so nothing else from the
v0.13 upgrade guide applies here.
